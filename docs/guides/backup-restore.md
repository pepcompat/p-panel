# Backup and restore

Back up host paths, application volumes and application databases with restic, prove the backups
restore, and restore data through a reviewed, approved plan. Verified end to end by
`scripts/lab/e2e_p6.py` (P6-T01 files, P6-T02 Postgres, P6-T03 production restore approval, P6-T04
interrupted backup, verification levels, maintenance report).

Design: [ADR-0009](../adr/0009-append-only-restic-with-separate-maintenance-identity.md). Each server
writes to its **own append-only** restic repository behind rest-server. Agents can create and read
snapshots but can never forget, prune or delete them. Retention, the offsite copy and lock removal run
from a separate **maintenance identity** that only the operator holds — the Center never stores it.

## Prerequisites and permissions

| Task                                                     | Permission                   | Built-in roles            | Extra                       |
| -------------------------------------------------------- | ---------------------------- | ------------------------- | --------------------------- |
| Create repositories, per-server access, mark initialized | `policies.manage`            | Platform Owner, Ops Admin | API only                    |
| Recovery export of repository passwords                  | `policies.manage`            | Platform Owner, Ops Admin | step-up, audited            |
| Policies, manual runs, verify, live snapshot list        | `backups.create`             | Platform Owner, Ops Admin | —                           |
| Plan, dry-run, execute a restore                         | `backups.restore`            | Platform Owner, Ops Admin | —                           |
| Approve a restore                                        | `approvals.decide`           | Platform Owner, Ops Admin | step-up; approver ≠ creator |
| Read repositories, policies, runs                        | `fleet.read` (server-scoped) | all four                  | —                           |

You need a backup host running rest-server with `--private-repos --append-only` for agents and a
separate full-access maintenance listener on the same data, reachable from the operator only. The agent
needs host `restic` ≥ 0.17 for paths targets and the `backup.helperImage` from its local config for
volume and database targets.

## 1. Repository and per-server access (once)

The **Repositories** tab shows repositories and their state; creating them is API-only:

```http
POST /backup-repositories
{ "name": "primary", "kind": "rest", "baseUrl": "https://backup.internal:8000", "offsite": { "kind": "s3", "endpoint": "…", "bucket": "…" } }
PUT  /backup-repositories/:id/servers/:serverId
{ "restUser": "node-a", "restPassword": "…" }          (repoPassword optional; generated by the Center)
```

Initialise the repository with the maintenance identity — agents cannot:

```bash
scripts/backup/maintenance.sh init <serverUser>
```

Then **Repositories → Mark initialized** (`POST /backup-repositories/:id/servers/:serverId/initialized`).
Runs against an uninitialised repository are refused (`REPO_NOT_INITIALIZED`).

**Escrow the repository passwords now**: **Repositories → Recovery export → Export recovery passwords**
with a 2FA code (`GET /backup-repositories/:id/recovery-export` + `X-Step-Up`). Shown once; store offline
(printed and sealed, or an age-encrypted file to an operator key). Repeat after adding a server. Without
these passwords the backups cannot be decrypted if the Center is lost (see
[RECOVERY_RUNBOOK.md](../RECOVERY_RUNBOOK.md) §2).

## 2. Policies

**Backups → Policies → + New policy**: **Policy name**, **Server**, **Repository**, **What to back up**
(**Host paths**, **App volume**, **App database**), **Schedule** (5-field cron + IANA timezone, with
presets and the next 3 runs), **Retention** (keep daily/weekly/monthly), **Verification** (after each
backup: nothing, repository check, or test restore; scheduled test restore: never, weekly, monthly),
**Enabled**.

API: `POST /backup-policies` (`PATCH` with `If-Match`; `DELETE` is a soft delete that keeps runs and
manifests).

- Paths must be absolute and canonical; `/`, `/proc`, `/sys`, `/dev`, `/run` and the agent dirs are
  refused (422 `BACKUP_TARGET_INVALID`).
- Database targets reference a Compose app's postgres or mysql service plus the **secret key** that holds
  the password; the password is read at run time and never stored in the policy.
- Retention is **recorded** here but applied by the maintenance script (`restic forget --prune`), not by
  agents or the panel.
- A run missed while the Center was down executes **once** on startup. Only one active run per policy; a
  slot that comes due during a run is skipped and audited.

## 3. Runs and verification

**Back up now** (`POST /backup-policies/:id/run` + `Idempotency-Key`) or wait for the schedule.
**Runs** tab → **Details** (`/backups/runs/:id`): snapshots, file manifest (path, size, sha256; up to
10 000 files), database manifest (tables and rows), job log.

A run is **Uploaded** only when every target produced a snapshot; anything else is **Failed**
(`BACKUP_PARTIAL`, `REPO_UNREACHABLE`, `REPO_LOCKED`, …). An interrupted backup never reports success.

Verification levels are honest:

| Badge                            | Meaning                                                     | How                                                    |
| -------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------ |
| Snapshot uploaded — not verified | the upload worked; nobody restored it yet                   | —                                                      |
| Repository checked               | `restic check` found the structure intact; no data restored | **Verify: check**                                      |
| Restore verified                 | an isolated restore matched the manifest                    | **Verify: test restore**, or a staging/scratch restore |
| Verification failed              | the last verification did not match                         | do not rely on it until re-verified                    |

`POST /backup-runs/:id/verify { "level": "check" | "restore_test" }`. A later `check` never downgrades
`restore_verified`.

**Snapshots** tab lists the repository live through the agent (`GET /servers/:id/snapshots`, read-only;
needs the agent online).

## 4. Restore

Start from an uploaded run: **Runs → Restore…** (`/restore/new`). The wizard steps are **Snapshot →
Target → Impact → Dry-run → Approval → Execution → Result**. A data restore is not a config or app
rollback, and an app rollback never restores data.

| Target mode                          | Effect                                                                       | Approval                               |
| ------------------------------------ | ---------------------------------------------------------------------------- | -------------------------------------- |
| Isolated staging copy (paths/volume) | restored next to the live data (new dir or new volume); nothing live touched | none outside production                |
| Scratch database                     | restored into an isolated DB container, compared, then removed               | none outside production                |
| In place — overwrite live data       | safety backup first, then overwrite                                          | **always**, plus any production target |

API flow (verified in `e2e_p6.py`):

```http
POST /restores                     { "runId": "…", "snapshotId": "…", "target": { … } }   → planned (impact computed)
POST /restores/:id/dry-run                                                                 → impact_reviewed
POST /restores/:id/approve         { "planHash": "…" }  + X-Step-Up  (other user)          → approved
POST /restores/:id/execute         { "confirmImpact": true }   (required for in_place)     → running → verified
```

- In-place restores require `confirmImpact: true` (else 422 `IMPACT_CONFIRMATION_REQUIRED`, audited) — the
  wizard's **I understand that … will be overwritten** box.
- Execute before approval → 409; the creator approving → 403; all audited.
- In-place execution: **Safety backup** (must upload) → **Stop app** → **Restore** → **Start app + health
  check** → **Verify**. An in-place database restore keeps the DB service running.
- **Cancel restore** is possible before it runs (`POST /restores/:id/cancel`).

## 5. Maintenance identity: prune, copy, check, unlock

Run on the backup host as the operator, with the maintenance credential from env/files (never argv):

```bash
scripts/backup/maintenance.sh --report https://<center> --repository-id <uuid> prune <serverUser> --keep-daily 7 --keep-weekly 4 --keep-monthly 6
scripts/backup/maintenance.sh --report https://<center> --repository-id <uuid> copy   <serverUser>   # offsite S3
scripts/backup/maintenance.sh --report https://<center> --repository-id <uuid> check  <serverUser> --read-data-subset 5
scripts/backup/maintenance.sh unlock <serverUser>        # clears REPO_LOCKED after a crash
scripts/backup/maintenance.sh snapshots <serverUser>     # read-only list
```

`--report` posts the outcome to `POST /backup-maintenance/reports` with `PPANEL_BACKUP_REPORT_TOKEN`, a
report-only token that cannot delete anything. **Repositories → Retention & offsite status** shows the
last report per kind (prune, offsite copy, check, unlock). Schedule these with cron or a systemd timer.

## Failure modes

| Symptom                                     | Meaning / recovery                                                                                                                               |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `REPO_NOT_INITIALIZED`                      | Run `maintenance.sh init`, then **Mark initialized**                                                                                             |
| `REPO_UNREACHABLE`                          | rest-server unreachable within 60 s (preflight `restic cat config`); nothing backed up                                                           |
| `REPO_LOCKED`                               | stale lock after an interrupted run: `maintenance.sh unlock <serverUser>`                                                                        |
| `BACKUP_PARTIAL`                            | not every target finished; the run is failed, fix the target and run again                                                                       |
| `BACKUP_IN_PROGRESS` / `VERIFY_IN_PROGRESS` | wait for the active run or verification                                                                                                          |
| Restore **Requires manual recovery**        | stopped part-way; the app may be stopped and data partly overwritten. See [emergency-recovery.md](emergency-recovery.md#restore-manual-recovery) |
| `backup_failed` incident                    | latest run failed/expired or verification failed ([alerts.md](alerts.md))                                                                        |

## Limitations

- Repositories and per-server access have no create form in the UI; use the API.
- Pruning and offsite copy are never triggered from the UI (by design).
- In-place restores of paths and volumes are covered by unit tests only, not in the lab. A failed volume
  staging restore leaves its new volume behind (agents never delete volumes).
- `backup.snapshots` and `backup.verify` need host restic even on Docker-only nodes.
- Database row counts in the manifest come from a read-only session after the dump, so they are not
  transactionally consistent with it.
- Snapshots taken after a Center restore are not re-imported as runs.
